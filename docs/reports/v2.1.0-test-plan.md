# v2.1.0 Test Plan

**Scope:** everything landed since `v2.0.1`, plus a smoke execution that
confirms the pipeline end to end.
**Supersedes:** `v2.0.0-test-plan.md` for the areas below; that plan remains
valid for everything it covered and is not withdrawn.

The automated suite is 1299 tests and green. This plan covers what those tests
**structurally cannot** reach: live provider behaviour, cross-stage ordering,
mailbox side effects, and anything whose failure looks like a plausible success.

> §19 of `requirements.md` states the cadence this follows: focused contract
> gates first, one controlled end-to-end smoke execution only after they pass,
> and smoke output treated as confirmation rather than primary defect discovery.

## 2. Focused gates

Run before any smoke execution. All are automated unless marked **manual**.

### 2.1 Schema and merge

- `pytest tests/test_manifest_parser.py tests/test_reservation_ingest.py`
- Booking fields accepted at both levels; unknown fields rejected
  (`additionalProperties: False`)
- Sidecar merge fills empty fields and **never** overwrites a manifest value
- Legs append, deduplicated by confirmation number
- **Merged sidecar content is re-validated against the schema** — a malformed
  extraction must fail the build, not reach the page
- Unknown destination id in a sidecar is skipped, not fatal

### 2.2 Matching

- All seven real Southwest reservations match their expected target
  (0.45–0.85). **Capitol Reef sits exactly on the 0.45 threshold with no
  margin** — if it drifts it goes to review, which is safe but should be
  noticed rather than discovered
- Gateway legs resolve trip-wide, not to the first/last stop
- A car matches its pickup; a flight matches whichever end is on the trip
- A booking below the unrelated floor stays out of the sidecar entirely
- A single shared token cannot alone clear the threshold

### 2.3 Privacy

- `pytest tests/test_main_requirements.py`
- `lodging.name`, `.website`, `.confirmation_number` and **both** transportation
  lists cleared under redaction
- `lodging.location` and `.checkin_time` deliberately **kept**
- **Manual:** grep a `prod` build for a known confirmation number and a known
  planning-link domain. Both must return zero. This is cheap and it is the
  check that would have caught the incident that created `--privacy-mode`

### 2.4 Rendering

- `pytest tests/test_html_assembler.py`
- `DRIVE_DESCRIPTIONS` keys == modal buttons, both directions. This pair has
  drifted twice and is now derived rather than recomputed; the test asserts the
  invariant, not the mechanism
- Booking cards absent entirely under redaction — not a greyed placeholder
- Every field originating from email is HTML-escaped
- Template checksum matches `checksums.txt`

## 3. Smoke execution

One controlled end-to-end run. Order matters: **eval first to inspect, prod
second to publish.** An unredacted build is the only place booking output is
visible, so inspecting after publishing inspects the wrong artifact.

### 3.1 Ingestion (only if bookings are in scope)

```bash
python scripts/ingest_reservations.py --manifest <path> --env-file <path> --dry-run
```

Verify before dropping `--dry-run`:

- [ ] Login succeeds; unread count matches expectation
- [ ] Each message classified sensibly; non-bookings are `none`
- [ ] Matches land on the right stops; gateway legs are trip-wide
- [ ] Anything for another trip reported as left in the inbox
- [ ] `pending` items are genuinely ambiguous, not mis-scored

Then run for real and confirm: sidecar written, handled messages filed to the
archive folder, unrelated messages **still unread in the inbox**.

### 3.2 Eval build

```
run-trip.BAT <program> eval
```

- [ ] `Privacy : off`
- [ ] `Bookings :` line reports the merged counts
- [ ] Publish **skipped** — environment is not prod
- [ ] Booking cards and trip-wide chips render; confirmation numbers legible
- [ ] **Manual read-through of one destination section.** The failure mode here
      is two cards that each look correct alone and contradict each other —
      travel time versus the day's schedule. No unit test catches that

### 3.3 Prod build

```
run-trip.BAT <program> prod
```

- [ ] `Privacy : redacted (…)` with non-zero counts
- [ ] Validation passes
- [ ] Publish fires; commit and push succeed
- [ ] Live page: no booking data, no planning links, `sw/dev` and `sw/eval` 404

### 3.4 Cost check

- [ ] Cost summary present, with `web_search` fees broken out
- [ ] A second consecutive run is materially cheaper than the first. Measured on
      the v2.0.1 line: **$2.86 cold → $0.17–0.33 warm**. If a warm run is not
      cheap, the persistent cache has regressed — which is exactly what happened
      when the test suite was clobbering it, silently, for weeks

## 4. Known-fragile areas

Not defects; places where a green suite is weaker evidence than it looks.

- **Warm-cache masking.** Most cost measurements are contaminated by a warm
  cache. A genuinely cold number needs a manifest whose destinations have never
  been harvested.
- **Quality-gate drift.** Attractions/restaurants pruned for unverified URLs
  varies run to run (18–26 observed on one manifest). Warnings, not errors, by
  design — but a sharp move is worth investigating.
- **Provider silence.** A provider can degrade without erroring; xAI's search
  was dead for an unknown period while the code read a parameter the API had
  stopped honouring. No test detects this. A periodic citation-fidelity probe is
  the mitigation and does not exist yet.
- **Ingestion is the highest-scrutiny surface.** IMAP credentials, untrusted
  email bodies, confirmation numbers. Schema re-validation and escaping
  constrain shape and rendering — neither prevents a plausible-looking *wrong*
  address from a hostile extraction.
