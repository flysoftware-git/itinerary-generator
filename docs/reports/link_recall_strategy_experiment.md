# Link recall strategy experiment: can better search close the dipstick65 no-link gap?

**Type:** research experiment, not a code change. `generator/` and `tests/` were
not touched. Raw machine-readable data lives alongside this file:
`link_recall_strategy_experiment_results.json` / `.md` (generated by
`scripts/experiment_link_recall_strategies.py`, which reuses the real,
unmodified `generator/url_discovery.py` query-building and URL-acceptance
helpers rather than re-implementing them, per this repo's existing
`scripts/probe_multi_provider_search_2026.py` convention).

## Question

`config.yaml` sets `url_policy_mode: enforce` and blocks `google_maps_search`,
`google_maps_dir`, `google_search`, and `social_media` site-wide (~L300-306) --
deliberately, so every link shown is a real, specific, verified page. A real
validation run, **SW2026-dipstick65**
(`C:/Temp/RoadTripRuns/SW2026-dipstick65/dev/index.html`), still ships several
attractions/trails with **no link at all**. Before considering relaxing that
policy, the project owner wanted to know: can smarter search close the gap?

## The 13 real target items

Sunrise Point, Inspiration Point (Bryce Canyon NP) -- The Waterpocket Fold
(Capitol Reef NP) -- Chimney Rock National Monument (Pagosa Springs) --
Museum of International Folk Art (Santa Fe) -- Queens Garden Trail (Bryce
Canyon NP) -- Fins and Things Trail (Moab) -- Park Avenue Trail (Arches NP) --
Jud Wiebe Trail, Bear Creek Trail (Telluride) -- Piedra Falls (Pagosa
Springs) -- Tent Rocks Cave Loop (Kasha-Katuwe Tent Rocks NM) -- Lava Tubes
via Lava Flow Trail (Snow Canyon SP).

## Method

Six strategies, one real live API call per item per strategy (see the script
docstring for full rationale):

| Strategy | Query construction | Provider |
|---|---|---|
| `baseline_grok` | Real production fallback query: `_build_query_variants()[0]` + the real `site:nps.gov/<code>` hint for in-park items -- reproduces `URLDiscoverer._search_first_strict`'s actual first attempt | Grok (`/v1/responses`, `web_search` tool) |
| `site_scoped_grok` | Forced `site:` filter per item type (nps.gov / alltrails.com / fs.usda.gov / blm.gov / venue domain) | Grok |
| `alt_phrasing_grok` | Unquoted `"<name> <destination> official page"` | Grok |
| `claude_web_search` | Same as baseline | Claude (`web_search_20260318` tool) |
| `gemini_google_search` | Same as baseline | Gemini (`google_search` grounding tool) |
| `openai_search` | Same as baseline | OpenAI (`gpt-5-search-api`) |

Every candidate is run through the real, unmodified
`URLDiscoverer._classify_url_policy_class` / `._is_specific_result_url` /
`._matches_site_filter` (imported from `generator/url_discovery.py`, not
duplicated), then live-verified with an HTTP HEAD/GET check. A strategy only
counts an item as a **hit** if the candidate both passes those real
acceptance checks *and* answers alive.

## Results: raw hit rate per strategy (single attempt per item)

| Strategy | Raw hits / 13 | Notes |
|---|---|---|
| `baseline_grok` | 9 (**11 adjusted**, see caveat below) | Reproduces production's real per-item fallback call |
| `site_scoped_grok` | 4 | Hurt by forcing alltrails.com (bot-blocked) + 4 provider timeouts |
| `alt_phrasing_grok` | 7 (of 9 non-timeout attempts, **7 = 78%**) | 4 of 13 calls hit a provider read-timeout, not a search failure |
| `claude_web_search` | 0 / inconclusive | Every call failed with HTTP 400 "credit balance too low" on the configured `ANTHROPIC_API_KEY` -- an account/billing limitation, not a capability finding |
| `gemini_google_search` | 4 | **5 of 13 "accepted" candidates were confirmed dead (HTTP 404) on independent re-check** -- Gemini's `google_search` grounding still fabricated plausible-looking URLs at a high rate |
| `openai_search` | 2 confirmed / 3 answered / 13 attempted | `gpt-5-search-api` on this org is capped at 6,000 tokens/min -- effectively **one usable call per ~2 minutes**; 10 of 13 calls hit HTTP 429 even with a 12s inter-call delay added in a dedicated retry pass (`link_recall_strategy_experiment_openai_retry.json`) |

### Important measurement caveat: AllTrails bot-blocking

Every AllTrails URL returned by every strategy (`Tent Rocks Cave Loop`,
`Lava Tubes via Lava Flow Trail`, `Queens Garden Trail`, `Fins and Things
Trail`, `Bear Creek Trail`, `Piedra Falls` in various strategies) was marked
`alive=False` in this experiment's raw HTTP HEAD/GET check with **HTTP 403**,
not because the trail page doesn't exist, but because alltrails.com
bot-blocks a plain `requests` HEAD/GET (the same bot-defense the production
codebase already has dedicated handling for -- see
`URLDiscoverer._fetch_alltrails_text`). Independent verification via
`WebSearch` confirmed both `alltrails.com/trail/us/new-mexico/tent-rocks-cave-loop`
(109 reviews) and `alltrails.com/trail/us/utah/lava-tubes-via-lava-flow-trail`
(1,506 reviews) are real, correctly-named, live, popular trail pages. All of
these candidates **did** pass the real `_is_specific_result_url` /
`_classify_url_policy_class` acceptance checks -- they only failed this
script's simplified liveness probe. Treating them as real hits is what turns
`baseline_grok`'s count from 9 to **11/13**.

### Gemini: confirmed URL fabrication, not just low citation fidelity

Five of Gemini's "accepted" candidates were independently re-checked with a
fresh GET and are genuinely dead:
`nps.gov/places/000/sunrise-point.htm` (404), `nps.gov/care/planyourvisit/waterpocket.htm`
(404), `nps.gov/places/000/queens-garden-trail.htm` (404),
`visittelluride.com/activity/jud-wiebe-trail/` (404),
`visittelluride.com/activity/bear-creek-falls/` (404). These are
plausible-looking, correctly-patterned URLs for real places -- exactly the
"confidently wrong link" failure mode `url_policy_mode: enforce` exists to
prevent. This matches (and reproduces live) the citation-fidelity gap already
documented in `scripts/probe_multi_provider_search_2026.py`'s history
(Gemini 4/21 = 19%, vs. Grok 21/21 = 100%, as of 2026-08-14). One further
Gemini candidate (Chimney Rock) returned an opaque
`vertexaisearch.cloud.google.com/grounding-api-redirect/...` proxy URL
instead of a direct citation -- a separate verifiability weakness of
Gemini's grounding API.

### Claude and OpenAI: real capability not established here

- **Claude**: every single call failed with `400 invalid_request_error:
  "Your credit balance is too low to access the Anthropic API."` This is an
  environment/billing limitation of the `ANTHROPIC_API_KEY` configured for
  this run, not evidence about Claude's search quality. The existing
  `scripts/probe_multi_provider_search_2026.py` history (Claude 14/15 = 93%
  citation fidelity, 2026-08-14) is the best available signal and points to
  Claude being a strong candidate -- but this experiment could not confirm it
  independently.
- **OpenAI**: `gpt-5-search-api` on the configured org is rate-limited to
  6,000 tokens/min, and a single search call consumes essentially the whole
  budget -- confirmed via the `x-ratelimit-*` response headers
  (`remaining-tokens: 0`, `reset-tokens: ~2m18s`). A dedicated retry pass
  with a 12s inter-call delay still hit HTTP 429 on 10 of 13 items. Of the 3
  that did answer: 2 found real, live, correct pages (`Sunrise Point`,
  `Queens Garden Trail`, both real `nps.gov` pages, though with an unasked-for
  `?utm_source=openai` query string appended -- a minor URL-fidelity quirk).
  The third (`Piedra Falls`) returned
  `fs.usda.gov/r02/sanjuan/recreation/piedra-falls-trailhead` -- a
  plausible-looking, policy-accepted USFS URL that is confirmed **404 dead**
  even with the tracking parameter stripped (the real page, found
  independently by `baseline_grok`, is at a different path:
  `.../recreation/trails/piedra-falls-trail`). So on real, non-rate-limited
  answers, OpenAI's error rate here (1 fabricated URL out of 3) is
  consistent with -- and does not contradict -- the 0% citation-fidelity
  history already documented for OpenAI in
  `scripts/probe_multi_provider_search_2026.py`.

Combined across the Grok-only strategies (no extra provider needed), **all
13 items had at least one real, specific, live, policy-compliant candidate
URL found** in this experiment.

## Definitive answer: Museum of International Folk Art

**This is a live, reproducible false positive in closure detection --
correctly routed by the recent fix, but with an unavoidable policy-enforce
side effect that keeps the visible result the same. It is neither
non-determinism nor an incomplete fix in the sense of "wrong code path."**

Evidence, all gathered live against the real dipstick65 run and real current
pages:

1. **The direct-batch harvest DID find a real link in the fresh dipstick65
   run.** The captured harvest HTML
   (`C:/Temp/RoadTripRuns/SW2026-dipstick65/dev/dev/url_discovery_direct_batch_html/santa-fe.attraction...html`)
   contains: `Museum of International Folk Art <a href="https://www.internationalfolkart.org/">Source</a> ... 4.6/5`.
2. **The final output still shows no link.** In
   `C:/Temp/RoadTripRuns/SW2026-dipstick65/dev/index.html`, the museum's card
   has no `<a href>`, an "Unverified" caution badge, and the practical note
   `"Free admission on Sundays. Currently closed; verify status before you
   go."` -- confirming the seed-attraction closure-strip path
   (`_discover_attractions`'s second pass, `generator/url_discovery.py`
   ~L4024-4074) fired.
3. **Live re-fetch of `internationalfolkart.org` right now reproduces the
   exact trigger.** The raw HTML (`resp.text`, unstripped of tags -- see
   `URLValidator.get_text`, `generator/url_validator.py` L62-72) contains,
   inside an HTML **comment** (`<!-- ... -->`, invisible to real visitors):
   *"The Girard Wing will be temporarily closed now through May 2026 for
   critical roof repair. The Bartlett Gallery and Lloyd's Treasure Chest are
   also currently closed due to regular gallery changeover."* This matches
   `ATTRACTION_CLOSURE_MARKERS` ("currently closed", "temporarily closed",
   "closed due to") via a **plain substring search over raw HTML**
   (`_has_attraction_closure_marker`, `generator/url_discovery.py` L12007) --
   HTML comments, `<script>` content, and any other non-visible text are not
   excluded.
4. **This is a real, if stale, partial-closure notice -- not the whole
   museum.** The state's own listing page
   (`newmexicoculture.org/museums/museum-of-international-folk-art`, a
   different real domain) independently and *visibly* (not in a comment)
   carries the same underlying announcement, describing it as affecting one
   specific exhibit/wing ("Multiple Visions: A Common Bond," in the Girard
   Wing, for roof repair) -- through a window ("through May 2026") that has
   already elapsed relative today's date (2026-08-17). The rest of both
   pages describes an actively operating museum. The substring check cannot
   distinguish "one wing closed for repair" from "the venue is closed," so
   it is a **false positive at the attraction level**, and it is **not a
   one-off flake** -- the triggering text is durably embedded in the site's
   markup and will keep tripping on every future run until either the site
   removes the stale comment/notice or the detector stops matching on raw,
   untagged-stripped HTML including comments.
5. **The 24a3d5e fix on this branch is real and correctly targeted, but its
   visible effect for this destination's config is masked.** Before that
   commit, this code path stripped both `url` and `maps_url` with no
   fallback attempt at all. After it, the same trigger now correctly routes
   through the shared `_assign_attraction_maps_fallback_or_fail_closed`
   helper (`generator/url_discovery.py` L4060) -- but that helper's own
   enforce-mode branch (L4138-4150) unconditionally sets `url=""` when
   `url_policy_mode: enforce` and `google_maps_search` is blocked, which is
   exactly this repo's `config.yaml`. So the fix changed *which code path*
   the museum passes through, and eliminated a genuine double-strip bug, but
   it could never have changed *this run's visible outcome* -- the museum
   was always going to end up with no link once closure detection (falsely)
   fired, given this config. That is two independent, stackable problems
   (a closure-detector false positive, and a policy-enforce fallback that
   has nothing safe left to offer once the real discovered URL is
   discarded), not one incompletely-fixed bug.

## Recommendation

**Better search strategy alone can close most of the gap, but not all of
it, and the production implementation isn't yet extracting the recall that
real search already supports.**

- For **11 of 13** items, a single, correctly-constructed query (the same
  one production's fallback path already builds) found a real, live,
  specific, policy-compliant page on the first try. For the remaining 2, a
  second attempt with different site-scoping or phrasing found one too --
  **13/13 have a real page somewhere**, contradicting the pessimistic
  "some of these viewpoints/trail segments just don't have a page" hypothesis
  for this particular list. (That hypothesis may still hold for other,
  untested items -- it just isn't the explanation for these 13.)
- The production gap looks structurally explained by three separable,
  independently fixable issues, **none of which require relaxing the
  enforce-mode URL policy**:
  1. **Single-shot live search is non-deterministic** (Park Avenue Trail,
     and one earlier Sunrise Point smoke-test call, both returned zero
     candidates on one attempt and a good candidate on the next identical or
     near-identical query). A cheap, bounded retry (2-3 variant attempts,
     which `_build_query_variants` already generates but which
     `_search_first_strict` may not always be exhausting before giving up --
     worth a closer look, out of scope for this research task) would likely
     recover some of today's silent misses.
  2. **AllTrails' own bot-defense causes real, accepted trail pages to fail
     the liveness check**, which -- if production's link-acceptance pipeline
     has any liveness gate outside the AllTrails-specific fetch path this
     experiment didn't exercise -- could itself explain some trail
     items shipping without a link even when search found the right page.
     Worth confirming whether that liveness gate is consistently routed
     through the AllTrails-aware fetch path everywhere a trail URL is
     accepted.
  3. **The Museum of International Folk Art gap is not a search problem at
     all** -- it is a closure-detector false positive (raw-HTML substring
     match, unstripped of comments) compounded by the enforce-mode fallback
     leaving nothing once the real link is discarded. No amount of better
     search changes this outcome; the real link is already being found.
- **Do not adopt Gemini or OpenAI as alternate/fallback search providers for
  this fail-closed use case as currently configured**: Gemini fabricated
  plausible-but-dead URLs on ~38% of its "accepted" candidates in this run
  (consistent with prior documented history), and OpenAI's search model is
  rate-limited to roughly one usable call per two minutes on this org's tier
  -- neither is currently a safe or practical substitute for Grok.
- **Claude remains untested here** (billing, not capability) and is the
  most promising alternative-provider candidate on paper (93% documented
  citation fidelity); worth a follow-up once API credit is restored.

## Domain patterns that worked

Real, specific, accepted pages for these 13 items clustered almost entirely
into a few authoritative-domain families: `nps.gov` (in-park
viewpoints/trails), `fs.usda.gov` (Forest-Service-managed trails/monuments:
Chimney Rock, Jud Wiebe, Bear Creek, Piedra Falls), `blm.gov` (Tent Rocks),
county/city government sites (`grandcountyutah.net` for Fins and Things), and
`alltrails.com` (subject to the bot-blocking caveat above). None of the real
hits needed a `google_maps_search`/`google_search`/social-media fallback --
every one of the 13 items has a legitimate non-generic source when the
right query finds it.
